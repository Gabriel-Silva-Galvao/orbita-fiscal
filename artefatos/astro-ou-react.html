Astro ou React para a área do assinante?

A landing capta e converte. Depois da compra, a pessoa ganha abas novas, que ainda não existem. Aqui está a comparação entre manter tudo em Astro, padronizar em React ou dividir o site, e com quais backends o Astro conversa.

Recomendação

Fique no Astro para o site inteiro. Faça as abas do assinante como páginas Astro renderizadas no servidor e use componentes React só nas partes muito interativas.

Um projeto só mantém o mesmo domínio, o mesmo login por cookie, os mesmos tokens da marca e um deploy só. A landing continua leve, porque só carrega JavaScript onde precisa. Separar em dois projetos só vale a pena se a área logada virar um aplicativo grande, com equipe própria.

Decisão tomada em 24/11/2026

O backend vai ser todo em Python, com FastAPI como biblioteca principal.

Login, assinatura, pagamento, portal e a base jurídica do plugin ficam nessa API. O Astro chama a API por HTTP e não guarda regra de negócio: o servidor do Astro só protege as rotas do assinante e repassa as chamadas.

Como o site está hoje

  • Astro 7.4, todo estático (sem adaptador de servidor), sem React. A interação é feita com scripts TypeScript simples, GSAP e Lenis.
  • As telas de Entrar, Checkout, Instalar e Portal (/conta) já existem em modo de demonstração e guardam a "assinatura" no navegador.
  • O .env.example já prevê endpoints externos para login, pagamento e contato. Ou seja, o projeto já foi pensado para conversar com um backend à parte.

React puro (B) só faria sentido se o site inteiro fosse um app. Ele não é: a parte que vende precisa ser rápida e encontrada no Google, e essa é justamente a força do Astro. A opção C resolve um problema que vocês ainda não têm, e cobra o preço de dividir login e marca em dois lugares.

  1. Páginas públicas continuam estáticas. Landing, Ajuda e textos legais são gerados no build, como hoje.
  2. Abas do assinante rodam no servidor. Com um adaptador instalado, cada rota logada recebe export const prerender = false e passa a ser montada a cada acesso, já com os dados da pessoa.
  3. Middleware guarda a porta. Ele confere a sessão antes de abrir qualquer rota em /conta e redireciona para /entrar quem não está logado.
  4. React só onde há interação pesada. Tabelas com filtro, histórico de pesquisas e editores entram como ilhas (client:load ou client:visible). O menu e o layout continuam em Astro.
  5. Formulários vão para a API em FastAPI. Cancelar plano, trocar e-mail e pedir reembolso viram rotas da API, com validação pelo Pydantic. O Astro chama essas rotas pelo servidor ou direto do React.

Quando reavaliar

Ainda no mesmo projeto

Se as abas virarem um app com muito estado no navegador, como navegação sem recarregar, tempo real ou editor de peças, monte um app React inteiro em /app com client:only="react". Ele continua dentro do Astro, com o mesmo login e a mesma marca.

Separar de verdade

Só se houver uma equipe dedicada à área logada, com ciclo de deploy próprio, ou um app mobile que reaproveite o mesmo código React. Nesse caso, a opção C passa a compensar.

Com quais backends o Astro se conecta

São duas camadas. O servidor do próprio Astro roda só JavaScript ou TypeScript. Ele cuida das páginas, do middleware, das Actions e dos endpoints. Já o backend de negócio pode ser escrito em qualquer linguagem: o Astro conversa com ele por HTTP (REST ou GraphQL), usando fetch no servidor.

Um detalhe sobre sessões: as sessões nativas do Astro precisam de um driver de armazenamento configurado (Redis, banco ou o padrão do adaptador) e não funcionam no middleware de borda (edge).

Próximos passos sugeridos

  1. Escolher onde hospedar e instalar o adaptador correspondente (npx astro add node ou cloudflare).
  2. Adicionar React com npx astro add react, só para as abas novas.
  3. Criar o middleware de login e marcar as rotas de /conta como renderizadas no servidor.
  4. Criar a API em Python com FastAPI e apontar os endpoints do .env para ela.
  5. README corrigido para Node 22, a versão mínima do Astro 6 em diante.
